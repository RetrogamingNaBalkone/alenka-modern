# Linux: сборка и границы проверки

## Разбор присланных изменений

Файлы `main.cpp`, `CMakeLists.txt` и `build-deb.sh`, полученные отдельно,
рассмотрены как предложенная реализация. Скрипт друга не запускался.

- В `main.cpp` изменены только два вызова: `SDL_GetTicks64()` заменён на
  `SDL_GetTicks()`. Это устраняет зависимость от SDL 2.0.18, но возвращает
  32-битное переполнение примерно через 49,7 суток. Тренажёр хранит время
  и дедлайны в 64 битах: простое расширение обнулившегося счётчика нарушает
  отсчёт времени и повтор клавиш. Вместо этого используется C++ `steady_clock`
  с миллисекундами от начала работы приложения.
- Поиск SDL через pkg-config нужен для старых пакетов без CMake-target
  `SDL2::SDL2`. В новой реализации используется импортированная цель
  `PkgConfig::SDL2_COMPAT`: она сохраняет найденные параметры компиляции
  и линковки, не перебирая вручную каталоги чужой архитектуры.
- Глобальные `link_libraries(stdc++fs)` и `--no-as-needed` из присланного
  CMake не нужны. Архивная библиотека должна следовать за использующим её кодом;
  `--no-as-needed` не исправляет порядок статических архивов. Теперь конфигурация
  проверяет компиляцию и линковку `std::filesystem` выбранным компилятором:
  сначала без дополнительной библиотеки, затем с `stdc++fs`. Зависимость
  передаётся через `alenka-original` всем использующим её целям.
- Добавление `stdc++fs` в ветку Windows ломает конфигурации без GNU-библиотеки,
  в частности MSVC. Эта правка не переносилась.
- GCC 7 не реализует используемый здесь `<filesystem>`. Для Bionic требуется
  GCC 8, который также обеспечивает целочисленный `std::from_chars`.
- Присланный скрипт использует общий `build/linux` для amd64 и i386,
  удаляет его перед конфигурацией, устанавливает пакеты на хост и применяет
  `--force-depends`, `--force-breaks`, `--force-conflicts` для SDL/Mir.
  Ошибки установки части необходимых пакетов допускают продолжение работы.
  Это не подходит как надёжный процесс выпуска. Новая сборка использует
  нативные архитектурные контейнеры и обычное разрешение зависимостей apt.
- Зависимости `.deb` в присланном скрипте заданы вручную и не доказывают
  совместимость полученного ELF. Теперь их вычисляет `dpkg-shlibdeps`.
- Запуск системного приложения не должен сохранять профили в случайную
  рабочую папку рабочего стола или `/usr`. Устанавливаемый launcher выбирает
  пользовательский каталог XDG. Бинарник находится в `/usr/lib/alenka-modern`,
  ресурсы — в `/usr/share/alenka-modern`, документация — в
  `/usr/share/doc/alenka-modern`. Launcher передаёт путь к ресурсам через
  `--data`. Формат сохранений не меняется.

Основания: [SDL_GetTicks64](https://wiki.libsdl.org/SDL2/SDL_GetTicks64),
[реализация filesystem в GCC 8](https://gcc.gnu.org/gcc-8/changes.html),
[импортированные цели pkg-config](https://cmake.org/cmake/help/latest/module/FindPkgConfig.html).

## Среда и проверка

Для Ubuntu 18.04 сохранена поддержка штатных CMake 3.10 и Python 3.6.
В `workspace.py` проверка вложенности каталогов больше не требует метода
`Path.is_relative_to`, появившегося в Python 3.9. Для CMake до 3.12 используется
`FindPythonInterp`; для новых версий — `FindPython3`.

`tools/build-linux.sh` собирает все цели, запускает CTest, устанавливает
portable-поставку во временный каталог и проверяет запуск из другого CWD
через Xvfb, без явного `--data`. Проверяются исходные байты ресурсов,
архитектура ELF, точный состав файлов, исполняемый бит и совпадение файлов
в tar.gz. Из готового `.deb` снова извлекаются файлы: проверяются системные
пути и совпадение байтов с portable-поставкой. Ресурсы в `/usr/lib` отклоняются.
Исходные DOS EXE, пользовательские профили и документация разработчика
в поставку не входят. Временное дерево удаляется при выходе.

### Сборка i386 на amd64

Без аргументов скрипт собирает архитектуру текущей системы. Команда
`bash tools/build-linux.sh i386` на amd64 включает GCC multilib (`-m32`),
выбирает SDL2 через pkg-config только из каталогов i386 и использует отдельный
каталог `build/linux-i386-cross`. Нативная i386-сборка остаётся в `build/linux-i386`.
Все тесты и smoke-проверки выполняют полученные 32-битные программы, поэтому
хост должен поддерживать запуск ELF i386.

Зависимости для Ubuntu 18.04 amd64 устанавливаются отдельно от скрипта:

Используйте отдельный контейнер или окружение без `libsdl2-dev:amd64`:
в Bionic dev-пакеты Mir двух архитектур конфликтуют. CI устанавливает только
SDL2 целевой архитектуры. Принудительное игнорирование зависимостей не требуется.

```sh
sudo dpkg --add-architecture i386
sudo apt-get update
sudo apt-get install g++-8-multilib cmake make python3 pkg-config libsdl2-dev:i386 libstdc++6:i386 dpkg-dev fakeroot xvfb xauth
CXX=g++-8 bash tools/build-linux.sh i386
```

В современных Ubuntu вместо `g++-8-multilib` используется `g++-multilib`,
а `CXX=g++-8` можно опустить. Зависимости deb вычисляет `dpkg-shlibdeps`
в окружении целевой архитектуры, заданном через `dpkg-architecture`.
Пакет `libstdc++6:i386` нужен отдельно от multilib: зависимости готового deb
должны ссылаться на runtime целевой архитектуры, а не на `lib32stdc++6` хоста.

GitHub Actions запускает нативные сборки в `ubuntu:18.04` и `i386/ubuntu:18.04`,
а также отдельную сборку i386 на amd64 через multilib.
Каждая среда устанавливает готовый `.deb` через apt и запускает launcher
от непривилегированного пользователя. Отдельная задача устанавливает
64-битный Bionic-пакет на Ubuntu 24.04 и проверяет современный компилятор.
Node-based actions выполняются на современном хосте, а не внутри Bionic.
Артефакт кросс-сборки называется `alenka-linux-i386-cross`; внутри него файлы
имеют целевую архитектуру `i386` в имени и метаданных deb. Проверка ELF
отклоняет бинарник другой архитектуры, даже если пакет назван правильно.

Для выпуска 2.0.1 обе задачи Bionic успешно собрали и проверили пакеты
amd64 и i386, включая установку и запуск от обычного пользователя.
Также успешно прошли установка Bionic-пакета на Ubuntu 24.04 и полная
сборка с тестами на современном компиляторе этой системы.
Результаты реальной Linux-проверки:
[GitHub Actions](https://github.com/RetrogamingNaBalkone/alenka-modern/actions/runs/42402165564).
Публикация пакетов в GitHub Releases не автоматизирована: workflow сохраняет
проверенные пакеты, архивы и SHA256 как артефакты сборки.

## AppImage в 2.0.2

AppImage собирается после нативного deb/tar.gz той же архитектуры, в той же
Ubuntu 18.04. Дополнительные зависимости упаковки и тестов:

```sh
sudo apt-get install ca-certificates desktop-file-utils appstream file xdotool openbox x11-utils
bash tools/build-appimage.sh
python3 tools/test_appimage_runtime.py artifacts/releases/alenka-modern-2.0.2-x86_64.AppImage
```

Runtime-тест запускайте от обычного пользователя. Для проверки именно FUSE-запуска
добавьте `--mounted`; без него проверяется извлечённое содержимое под Xvfb.
Готовый AppImage также поддерживает `--appimage-extract-and-run` без FUSE.

`resources/appimage-tools.json` закрепляет asset ID и SHA256 linuxdeploy,
appimagetool и runtime для каждой архитектуры. Даже кэш проверяется перед
использованием. Во время упаковки инструменты извлекаются без FUSE.
AppImage включает SDL2, libstdc++ и их зависимости; системные libc и загрузчик
не включаются. Для каждой включённой библиотеки сохраняются copyright и
сведения о версии исходного пакета с URL в Launchpad.

`AppRun` определяет каталог своего образа до смены рабочей папки. Ресурсы
находятся в `usr/share/alenka-modern`, профили — в пользовательском XDG-каталоге.
Проверяются исходные ресурсы, архитектура всех ELF, отсутствие зависимостей
от GLIBC новее 2.27, разрешение библиотек, метаданные и контрольные суммы.
Runtime-тест переносит образ в путь с пробелами, запускает его из `/usr`,
переключает звук через SDL-ввод и проверяет сохранение после перезапуска.
В CI этот тест выполняется на Bionic и на чистой Ubuntu 24.04 без системной SDL2.

При локальной сборке в WSL используйте файловую систему Linux, например
каталог в `~/src`: deb требует Unix-права, которых может не быть у файлов
на `/mnt/c`. Готовые пакеты можно копировать обратно на диск Windows.
