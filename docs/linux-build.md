# Linux: сборка и границы проверки

## Разбор присланных изменений

Файлы `main.cpp`, `CMakeLists.txt` и `build-deb.sh`, полученные отдельно,
рассмотрены как предложенная реализация. Скрипт друга не запускался.

- В `main.cpp` изменены только два вызова: `SDL_GetTicks64()` заменён на
  `SDL_GetTicks()`. Это устраняет зависимость от SDL 2.0.18, но возвращает
  32-битное переполнение примерно через 49,7 суток. Тренажёр хранит время
  и дедлайны в 64 битах: простое расширение обнулившегося счётчика нарушает
  отсчёт времени и повтор клавиш. Вместо этого используется C++ `steady_clock`
  с миллисекундами от начала работы приложения.
- Поиск SDL через pkg-config нужен для старых пакетов без CMake-target
  `SDL2::SDL2`. В новой реализации используется импортированная цель
  `PkgConfig::SDL2_COMPAT`: она сохраняет найденные параметры компиляции
  и линковки, не перебирая вручную каталоги чужой архитектуры.
- Глобальные `link_libraries(stdc++fs)` и `--no-as-needed` из присланного
  CMake не нужны. Архивная библиотека должна следовать за использующим её кодом;
  `--no-as-needed` не исправляет порядок статических архивов. Теперь конфигурация
  проверяет компиляцию и линковку `std::filesystem` выбранным компилятором:
  сначала без дополнительной библиотеки, затем с `stdc++fs`. Зависимость
  передаётся через `alenka-original` всем использующим её целям.
- Добавление `stdc++fs` в ветку Windows ломает конфигурации без GNU-библиотеки,
  в частности MSVC. Эта правка не переносилась.
- GCC 7 не реализует используемый здесь `<filesystem>`. Для Bionic требуется
  GCC 8, который также обеспечивает целочисленный `std::from_chars`.
- Присланный скрипт использует общий `build/linux` для amd64 и i386,
  удаляет его перед конфигурацией, устанавливает пакеты на хост и применяет
  `--force-depends`, `--force-breaks`, `--force-conflicts` для SDL/Mir.
  Ошибки установки части необходимых пакетов допускают продолжение работы.
  Это не подходит как надёжный процесс выпуска. Новая сборка использует
  нативные архитектурные контейнеры и обычное разрешение зависимостей apt.
- Зависимости `.deb` в присланном скрипте заданы вручную и не доказывают
  совместимость полученного ELF. Теперь их вычисляет `dpkg-shlibdeps`.
- Запуск системного приложения не должен сохранять профили в случайную
  рабочую папку рабочего стола или `/usr`. Устанавливаемый launcher выбирает
  пользовательский каталог XDG, а бинарник и ресурсы остаются в
  `/usr/lib/alenka-modern`. Формат сохранений не меняется.

Основания: [SDL_GetTicks64](https://wiki.libsdl.org/SDL2/SDL_GetTicks64),
[реализация filesystem в GCC 8](https://gcc.gnu.org/gcc-8/changes.html),
[импортированные цели pkg-config](https://cmake.org/cmake/help/latest/module/FindPkgConfig.html).

## Среда и проверка

Для Ubuntu 18.04 сохранена поддержка штатных CMake 3.10 и Python 3.6.
В `workspace.py` проверка вложенности каталогов больше не требует метода
`Path.is_relative_to`, появившегося в Python 3.9. Для CMake до 3.12 используется
`FindPythonInterp`; для новых версий — `FindPython3`.

`tools/build-linux.sh` собирает все цели, запускает CTest, устанавливает
portable-поставку во временный каталог и проверяет запуск из другого CWD
через Xvfb, без явного `--data`. Проверяются исходные байты ресурсов,
архитектура ELF, точный состав файлов, исполняемый бит и совпадение файлов
в tar.gz. Из готового `.deb` снова извлекаются файлы и сверяются с архивом.
Исходные DOS EXE, пользовательские профили и документация разработчика
в поставку не входят. Временное дерево удаляется при выходе.

GitHub Actions запускает сборку в `ubuntu:18.04` и `i386/ubuntu:18.04`.
Каждая среда устанавливает готовый `.deb` через apt и запускает launcher
от непривилегированного пользователя. Отдельная задача устанавливает
64-битный Bionic-пакет на Ubuntu 24.04 и проверяет современный компилятор.
Node-based actions выполняются на современном хосте, а не внутри Bionic.

Локальная проверка на Windows не подтверждает выполнение в Linux.
До успешного прохождения обеих задач Bionic и задачи Ubuntu 24.04
совместимость и готовность Linux-релиза остаются неподтверждёнными.
Публикация пакетов в GitHub Releases не автоматизирована: workflow сохраняет
проверенные пакеты, архивы и SHA256 как артефакты сборки.
